# 「多 vDCU 并发启动密度测试升级（vLLM/SGLang 实例）」测试方案（总结版）

依据：《vDCU 虚拟化测试方案_v1.2_20261102》VDCU-CTR-016（单卡 4 vDCU 四容器并发启动密度【通过】）、VDCU-INF-006（多实例并发推理【通过】）、《vDCU 容器挂载测试》多容器场景，及组长对 CTR-016 的新要求（2026-11 会议纪要）。

## 1. 现状与问题背景

1. **CTR-016 现状**：4 个容器各绑 1 个 vDCU，并发启动 + 并发执行 `hy-smi` 查询 + 并发跑**短时 HIP 样例**即判通过。HIP 样例只做一次矩阵乘，不能代表真实推理服务的启动与运行行为。
2. **组长披露的已知 bug**：旧版 DTK（对话记录为 **2625004**，疑为旧 DTK 版本号，待核实）存在缺陷——**同一物理卡上多个 vDCU 同时启动时，即使显存充足，第二个实例也起不来**。
3. **缺陷触发路径**：64 GB 卡二等分成两个 32 GB vDCU；vDCU0 已占用约 30 GB，vDCU1 完全空闲（32 GB 可用、应能启动），但 vLLM 的 **V1 engine** 调用 DTK 底层的 **heap memory 相关接口**时触发错误，导致 vDCU1 上的实例启动失败。
4. **修复状态**：该问题在 **DTK 26.10** 应已修复，需复测验证（当前环境：DTK 26.10 / vLLM 0.28.1rc1 / hy-smi 1.27.0）。

## 2. 组长要求提炼（对话 → 验证要求）

1. **负载升级**：并发启动密度测试不再只用短 HIP 样例，改用 **vLLM 或 SGLang 实例**（优先 vLLM/SGLang）；
2. **同步并发**：多个实例**同时启动**，启动成功后**同步并发发送推理请求**（"同步推"），验证每个实例真实可用；
3. **回归重点**：显存充足但第二个实例起不来的历史 bug（2625004）需在 DTK 26.10 上复测确认已修复；
4. **复现场景模板**：同卡二等分 → vDCU0 先占 ~30 GB → vDCU1 空闲 32 GB 启动 vLLM 实例 → 应成功启动并正常推理。

## 3. 测试目标

| 目标 | 说明 |
| --- | --- |
| T1 并发启动密度 | 同卡 4 等分 4 容器 / 2 等分 2 容器，同步并发启动 vLLM 实例全部成功 |
| T2 并发推理可用 | 各实例就绪后同步并发压测，全部正常返回 |
| T3 历史 bug 回归 | 复现"vDCU0 占 30G + vDCU1 空闲启动"场景，验证 26.10 无 heap memory 接口报错 |
| T4 启动时序覆盖 | 同时启动与先后启动（第一个运行中再起第二个）两种时序均验证 |

## 4. 测试用例设计

### 4.1 前置准备

- 镜像：`inference_image`（vLLM 0.28.1rc1，默认 V1 engine）；SGLang 镜像现场具备时补充对照；
- 模型：MiniCPM5-1B-SFT（约 1.1B，/workspace/openbmb--MiniCPM5-1B-SFT），四等分 16 GB 实例须按配额约束 `--max-model-len` / `--gpu-memory-utilization`，避免显存不足干扰结论；
- 压测工具：`vllm bench serve` 或等价并发请求脚本；
- 记录启动日志中的引擎版本（"Using V1 LLM engine"），确认缺陷触发路径所依赖的 V1 engine 已生效。

### 4.2 用例详情

**CN-001 并发启动密度基线（改造 CTR-016）**
1. 卡 A 四等分创建 vdev0~vdev3，4 个容器各绑一个，同步并发启动 vLLM 实例；
2. 记录每个容器启动耗时、退出码、就绪时间（轮询 /v1/models）；
3. 4 个实例全部就绪后，**同步并发**发送推理请求（各实例 ≥ 100 条，input 512 / output 1）；
4. 预期：4 实例全部启动成功、并发压测全部正常返回；记录各实例吞吐与 P50/P95/P99。

**CN-002 二等分 2 实例并发（与历史 bug 同构形态）**
1. 卡 A 二等分创建 vdev0/vdev1，2 容器同步并发启动 vLLM 实例；
2. 就绪后同步并发压测；
3. 预期：2 实例全部成功（历史 bug 形态下无异常）。

**CN-003 显存紧张场景回归（核心，复现 2625004）**
1. 卡 A 二等分（32 GB × 2）；
2. 容器 A 绑 vdev0，启动 vLLM 实例并使显存占用约 **30 GB**（大模型 / 高 KV cache / 长序列压测均可），保持服务运行；
3. 观测宿主机 `--show-vdevice-info` 确认 vdev0 Usage memory ≈ 30 GB、vdev1 空闲；
4. 容器 B 绑 vdev1 启动 vLLM 实例（32 GB 可用，应能启动）；
5. 启动成功后同步并发压测，验证推理正常；
6. 预期（DTK 26.10 已修复）：B 正常启动与推理，无 heap memory 接口报错；若失败，记录完整报错日志（关键词：heap memory / hipErrorOutOfMemory / V1 engine）并存档上报。

**CN-004 启动时序覆盖**
1. 同时启动：CN-001 已覆盖；
2. 先后启动：容器 A 先启动并完成模型加载、开始压测后，容器 B 再启动实例，验证第二个实例不受同卡第一个实例运行状态影响；
3. 预期：两种时序下第二个实例均正常。

**CN-005 SGLang 实例对照（可选）**
1. 现场具备 SGLang 镜像时，按 CN-002 形态启动 2 实例并发压测；
2. 预期：与 vLLM 结论一致；若出现框架差异，记录框架版本与报错。

**CN-006 结果归档与上报**
1. 汇总各形态的启动时序、显存占用曲线、压测吞吐与报错日志；
2. 回归结论写入报告：2625004 问题在 DTK 26.10 上已修复（PASS）或复发（ISSUE 记录 + 驱动团队沟通）。

## 5. 观测点与判定

| 观测点 | 判定 |
| --- | --- |
| 各实例启动退出码 / 就绪时间 | 全部 rc=0 且 /v1/models 就绪 |
| 同步并发压测 | 各实例请求全部正常返回，无超时/报错 |
| 宿主机 `--show-vdevice-info` | 各 vDCU Usage memory 与各自实例占用对应，无跨 vDCU 串扰 |
| 失败日志关键词 | 出现 heap memory / OOM / V1 engine 报错 → 判定回归失败 |
| 引擎版本 | 确认 V1 engine 生效（缺陷触发路径成立的前提） |

## 6. 自动化脚本改造建议

当前自动化未实现 CTR-016（[ctr.py](cases/ctr.py) 仅到 CTR-012），建议新增：

1. `ctr_016`：4 等分 4 容器，`ctx.docker(... detach=True)` 同步启动 vLLM 实例，复用 [vllm_smoke.py](assets/vllm_smoke.py) 的启动/就绪轮询/请求逻辑；
2. `ctr_016b`（CN-003 回归）：先起占用容器（30 GB 显存占用，可复用 [fun.py](cases/fun.py) `HOLD_DEVICE` 或大模型实例），再起第二实例，断言 `VLLM_RESULT` 出现；
3. 同步启动用 `detach=True` + 启动完成后统一 `docker wait`/轮询就绪，避免串行掩盖时序问题；
4. 压测并发通过 `vllm bench serve` 的 `--max-concurrency` 或多进程请求脚本实现；
5. 每实例原始日志存档到报告 steps，便于回归失败时取证。

## 7. 风险与注意事项

- **版本号核实**：对话记录的 "2625004" 需与组长确认确切的旧 DTK 版本，写入报告的"已知缺陷版本"字段；
- **四等分显存紧张**：16 GB 配额下必须限制 `--max-model-len`，避免把"显存不足"误判为历史 bug 复发（判据以 CN-003 的 32 GB 场景为准）；
- **V1 engine 前提**：vLLM 0.28.1rc1 默认 V1 engine，启动日志需确认；若镜像配置回退 V0，需重新评估触发路径；
- **与 INF-006 的边界**：INF-006 验证的是"多实例并发推理吞吐"，本方案验证的是"并发启动密度 + 历史 bug 回归"，两者可共用容器形态但判定目标不同。
