# 「HCU/DCU 资源名前缀配置化」测试方案（总结版）

依据：《vDCU 虚拟化测试方案_v1.2_20261102》附录 B YAML 模板（B.1 vHCU Pod 算力+显存、B.2 物理整卡 Pod）、《HCU Device Plugin-v3.0.1》第 4 章与 5.1 节，及组长对 B.1 模板的新要求（2026-11 会议纪要）。

## 1. 背景与版本演进

1. **开源前**：设备插件 3.0 / 3.0.0 之前，资源名统一使用 **DCU 前缀**：`hygon.com/dcunum`、`hygon.com/dcucores`、`hygon.com/dcumem`；
2. **开源合规审查**：DCU 写法不允许，全部改为 **HCU 前缀**：`hygon.com/hcunum`、`hygon.com/hcucores`、`hygon.com/hcumem`，最新驱动均已变为 HCU（见《HCU Device Plugin-v3.0.1》5.1）；
3. **3.0.0 / 3.0.1 硬切换问题**：这两个版本将前缀暴力切换为 HCU，部分存量用户不接受、无法平滑升级；
4. **后续规划**：前缀改为**配置字段**，用户可自行配置为 GPU / DCU / HCU 等任意值（金龙、得闯负责改造）；
5. **v1.2 方案的小错误**：附录 B.1/B.2 模板仍写 `hygon.com/dcunum`，与官方文档（hcunum）及最新驱动不一致，需要修正并说明前缀可配置。

## 2. 组长要求提炼（对话 → 验证要求）

1. **双前缀覆盖**：同一机线（环境）上**既测一次 HCU 前缀、又测一次 DCU 前缀**；
2. **自动化脚本适配**：资源名前缀在脚本中做成可配置项，不再写死；
3. **自定义前缀压测**：既然组件支持配置，就把前缀**配置成自定义值（如 GPU）**跑通全流程，专门用来发现这个组件的 bug；
4. **模板修正**：附录 B 模板按"前缀可配置"口径修正，并注明版本对应关系。

## 3. 测试目标

| 目标 | 说明 |
| --- | --- |
| T1 双前缀功能一致性 | 同一环境下 HCU 与 DCU 前缀的 Pod 申请、调度、设备可见、回收行为一致 |
| T2 自定义前缀可用性 | 配置为 GPU 等任意前缀后全流程可用 |
| T3 组件健壮性 | 前缀边界值（大小写、非法字符、空值）下组件不崩溃、报错明确 |
| T4 脚本适配 | 自动化脚本按前缀配置参数化，B.1/B.2 模板同步修正 |

## 4. 测试用例设计

### 4.1 前置准备

- 记录插件版本（当前环境 dcu-device-plugin v2.4.2；官方文档 v3.0.1）、驱动版本；
- `kubectl describe node <node>` 记录实际注册的资源名（hcunum 或 dcunum），作为"当前前缀"基线；
- 确认组件是否已具备前缀配置能力（配置字段位置：部署 YAML 环境变量 / ConfigMap）；若当前版本不支持配置，先按当前前缀执行 T1，T2/T3 标记为"待配置化版本上线后执行"。

### 4.2 用例详情

**PX-001 前缀现状确认**
1. 查看设备插件 Pod 的环境变量与节点 allocatable；
2. 记录当前注册前缀及三类资源（num/cores/mem）的容量；
3. 预期：前缀与插件版本对应关系明确（3.0.0/3.0.1 = HCU；更早 = DCU），写入报告环境信息。

**PX-002 HCU 前缀全流程（当前版本基线）**
1. 以 `hygon.com/hcunum: 1 + hcucores: 25 + hcumem: 16384` 提交 Pod；
2. 验证 Running、容器内 `hy-smi virtual --show-device-info` 配额正确（30 CU / 16 GB 量级）、运行 HIP 样例；
3. 删除 Pod 后确认资源回收；
4. 预期：全流程正常。

**PX-003 DCU 前缀全流程（同机线复测）**
1. 在支持 DCU 前缀的插件版本环境（或配置切换后），以 `hygon.com/dcunum: 1 + dcucores: 25 + dcumem: 16384` 重复 PX-002 全流程；
2. 预期：与 HCU 前缀行为一致，仅资源名不同。

**PX-004 自定义前缀压测（核心，发现组件 bug）**
1. 将前缀配置为自定义值，如 **GPU**（即 `hygon.com/gpunum`、`hygon.com/gpucores`、`hygon.com/gpumem`）或 DCU/HCU 之外的任意合法字符串；
2. 验证：插件启动正常、节点 allocatable 按新前缀注册、Pod 以新前缀申请可调度、容器内设备可见且配额正确、删除后回收正常；
3. 顺带验证配置化改造的兼容承诺：DCU、HCU、GPU 三种配置均可用；
4. 预期：三种前缀下功能一致；任何前缀下的异常（注册缺失、调度失败、配额错误、回收残留）均为组件 bug，逐项记录并上报。

**PX-005 前缀边界与异常输入**
1. 非法值测试：空字符串、大小写混用（如 `Dcu`）、含特殊字符（如 `HCU-1`）、超长前缀；
2. 记录组件行为：拒绝部署（报错明确）还是静默异常；
3. 预期：非法输入被明确拒绝且错误信息可读，组件不崩溃。

**PX-006 前缀切换与共存**
1. 从 HCU 切换到自定义前缀后：已有 Pod 是否受影响、新 Pod 按新前缀申请是否正常、旧前缀资源是否正确注销；
2. 混用场景：切换过程中同时提交新旧前缀 Pod，观察调度与资源计数；
3. 预期：切换后旧前缀不再可申请，已运行 Pod 不受影响（或以文档约定行为为准并记录）。

## 5. 结果判据

- PX-002/003：HCU 与 DCU 前缀同机线全流程 PASS，行为一致；
- PX-004：DCU/HCU/GPU 三种配置均可正常申请与回收（配置化功能验证）；发现的问题逐项记录为组件 bug；
- PX-005：非法前缀被明确拒绝；
- 附录 B 模板修正：资源名前缀标注为"可配置（默认 HCU，可配 DCU/GPU 等）"，并给出两种前缀的示例。

## 6. 自动化脚本改造建议

现行自动化 [cluster.py](cases/cluster.py) 的 `_resource_mode()` 仅识别 `hygon.com/dcunum` 与 `hygon.com/dcu` 两种。改造点：

1. [config.json](config.json) 增加 `resource_prefix` 配置项（如 `hcunum` / `dcunum` / `gpunum`，含 cores/mem 派生），支持 `VDCU_RESOURCE_PREFIX` 环境变量覆盖；
2. `_resource_mode()` 泛化为「按配置前缀探测 + 回退自动识别」，识别结果打印到报告（PX-001 自动化）；
3. K8S/HAMI/VOL 各用例的 Pod 模板（`_pod_manifest`）统一从配置读取前缀生成 resources 字段；
4. 新增 `k8s_prefix` 用例组：同一环境分别以 HCU/DCU/自定义前缀各跑一遍 K8S-002 全流程（申请→可见→回收），对比结果；
5. 前缀合法性校验（正则白名单）放脚本预检，PX-005 的非法输入先由脚本拦截，再手工验证组件侧行为。

## 7. 风险与注意事项

- **版本对应关系**：资源名前缀与插件版本强相关（≥3.0.0 = HCU；<3.0 = DCU），双前缀同机线测试受插件版本限制，若当前插件只支持单前缀，DCU 前缀用例标记"待版本支持"并说明；
- **以实测为准**：节点实际注册名以 `kubectl describe node` 为准，不以前缀配置项假设为准；
- **配置化未上线时的执行策略**：若被测版本尚未支持前缀配置，PX-004/005 列为后续跟踪用例，先把 PX-002/003 与脚本适配做完；
- **与 B.1 模板联动**：方案修正后的模板应同步到附录 B，避免再次出现 dcunum/hcunum 混用。
