# 「同一 vDCU 多容器绑定互斥问题排查」测试方案（总结版）

依据：《vDCU 虚拟化测试方案_v1.2_20261102》VDCU-CTR-012（同一 vDCU 绑定到第二个容器（互斥）【预期失败】、ISSUE-012）、《vDCU 容器挂载测试》多容器场景（场景一/三），及组长对该用例的新要求（2026-11 会议纪要）。

## 1. 问题现状（已确认的事实）

1. **互斥未实现**：自动化实测（2026-11-02，驱动 6.4.2-V2.1.0）第二条容器仍可使用已被占用的 vDCU，CTR-012 以 XFAIL（ISSUE-012）记录。
2. **占用保护连带失效**：同一轮实测中 FUN-016/017 FAIL——使用中的 vDCU 执行 `--destroy-vdevices` / `--update-vdevice` 未被拒绝，直接返回 "destroyed/updated successfully!"。
3. **宿主机侧占用观测不稳定**：部分轮次 FUN-016/017 因「等待容器占用设备超时（Usage memory 未出现）」失败，宿主机 `--show-vdevice-info` 的占用字段观测存在不可靠现象。
4. 方案正文 3.3 已声明边界：手工挂载允许重复使用时"不能据此宣称底层已实现互斥"；组长要求在此基础上进一步排查监控机制本身。

## 2. 组长要求提炼（对话 → 验证要求）

1. **设计意图**：同一 vDCU 绑定到容器应当互斥，由驱动侧控制；当前多个容器可同时绑定成功，属于设计缺陷。
2. **核心观测点**：vDCU 被容器占用时，宿主机执行 `hy-smi virtual --show-vdevice-info` 应显示每个 vDCU 关联的 **container id**；需验证该字段是否存在、是否正确、多容器绑定时如何表现。
3. **扩展压力验证**：不止起 2 个，要起 **3 个、4 个容器**绑同一 vDCU，若都能启动即为问题。
4. **真实负载要求**：占用容器必须运行 **vLLM 或 PyTorch 实例**（真实业务负载），在负载运行状态下观测，而非 sleep 占位。
5. **监控影响面**：K8S 上层已限定一 vDCU 一绑；但若 K8S 调度的同时其他人在手工容器里占着同一 vDCU，监控必出问题——包括上层 **exporter** 的指标异常。
6. **后续路径**：确认问题后与驱动团队沟通修复；产出可作为沟通依据的完整证据材料。

## 3. 排查目标

| 目标 | 说明 |
| --- | --- |
| T1 互斥行为 | 2/3/4 个容器绑定同一 vDCU 时，驱动是否拒绝后续绑定 |
| T2 container id 监控 | `--show-vdevice-info` 是否输出关联 container id；空闲/占用/多容器三种状态下的正确性；容器退出后是否清除 |
| T3 真实负载下观测 | vLLM/PyTorch 实例运行期间宿主机侧字段变化（container id、Usage memory、Dev busy percent） |
| T4 上层影响 | K8S Pod 与手工容器并存冲突时，调度、监控与 exporter 指标的表现 |
| T5 证据产出 | 面向驱动团队的缺陷确认报告（版本、命令、原始输出、时间线） |

## 4. 测试用例设计

### 4.1 前置准备

- 记录环境：驱动版本、hy-smi 版本、Docker 版本、K8S 设备插件版本；
- 创建二等分 vDCU（vdev0/vdev1），记录空闲态 `--show-vdevice-info` 原始输出作为基线；
- 若现场部署了 exporter，记录其监控指标基线。

### 4.2 用例详情

**MX-001 互斥基线复现（改造 CTR-012）**
1. 容器 A 挂载 vdev0.conf 并运行 PyTorch 持续负载（矩阵乘循环，显存占用 ≥ 4 GB）；
2. 负载运行中，容器 B 用同一 vdev0.conf 启动并执行设备查询 + HIP 样例；
3. 记录容器 B 的启动结果与完整输出；
4. 预期（按设计）：B 绑定被拒绝或不可用；实际行为如实记录。

**MX-002 多容器叠加压力（2/3/4 容器）**
1. 保持容器 A 负载运行，依次追加容器 B、C、D（均绑同一 vdev0.conf）；
2. 每个容器内执行 `hy-smi virtual --show-device-info` 与 HIP 样例；
3. 每追加一个容器，立即在宿主机执行 `--show-vdevice-info` 并保存原始输出；
4. 重点记录：能起来几个？各容器是否都能算？宿主机侧 container id 如何变化？

**MX-003 container id 关联字段核查（核心）**
1. 空闲态：宿主机 `--show-vdevice-info` 中 vdev0 是否包含 container id 字段（期望：无或空）；
2. 单容器占用：启动负载容器 A，观测字段出现情况、值与 `docker inspect` 实际容器 ID 是否一致；
3. 多容器占用：叠加 B/C/D 后，观测字段是显示第一个、最后一个、多个还是异常值；
4. 容器退出：依次停止各容器，观测字段何时清除、是否残留；
5. 交叉验证：同卡 vdev1 保持空闲作为对照，确认字段变化只发生在被占用的 vDCU 上。

**MX-004 vLLM/PyTorch 真实负载下的观测**
1. 容器 A 内启动 vLLM 服务（或 PyTorch 训练）并确认已加载模型/显存占用；
2. 负载运行期间，按 5 秒间隔连续采样宿主机 `--show-vdevice-info` ≥ 2 分钟；
3. 记录 container id、Usage memory、Dev busy percent 的时序变化；
4. 再叠加容器 B 重复采样，对比字段漂移。

**MX-005 K8S 与手工容器并存冲突（监控影响面）**
1. 通过设备插件创建占用同一物理卡资源的 Pod（正常调度路径）；
2. Pod 运行期间，在宿主机手工启动容器绑同一 vdev 配置；
3. 观测：手工容器是否可绑定成功；宿主机监控字段是否混乱；exporter（如有）上报的占用指标是否异常；
4. 记录冲突场景下 hy-smi 各查询命令的输出。

**MX-006 证据整理与上报**
1. 汇总 MX-001~005 的原始输出、时间线与判定结论；
2. 与"设计意图"对照形成缺陷描述（互斥缺失 + container id 监控异常 + exporter 影响）；
3. 提交驱动团队，更新 ISSUE-012 并跟踪修复版本。

## 5. 观测点与判定矩阵

| 状态 | container id 期望（按设计） | 判定 |
| --- | --- | --- |
| 空闲 | 无关联容器 | 出现残留值 → 缺陷 |
| 单容器占用 | 显示该容器真实 ID | 不显示/显示错误 → 缺陷 |
| 多容器占用 | 拒绝后续绑定，只保留首个 | 全部绑定成功或字段异常 → 缺陷 |
| 容器退出 | 字段清除、可重新绑定 | 残留/无法再绑 → 缺陷 |

任一判定项不符即纳入缺陷报告；全部符合但互斥仍缺失时，说明监控字段独立于互斥逻辑，同样需与驱动团队对齐设计。

## 6. 自动化脚本改造建议

现行 `cases/ctr.py` 的 `ctr_012`（[ctr.py:195-210](cases/ctr.py#L195-L210)）仅做"第二个容器能否用"的单点断言，且占用容器只跑 `sleep 120`。改造点：

1. 占用负载由 sleep 改为 PyTorch 显存占用循环（复用 [fun.py](cases/fun.py) 的 `HOLD_DEVICE`）；
2. 参数化容器数量（2/3/4），逐次启动并断言；
3. 每步在宿主机采样 `--show-vdevice-info -d <card>` 原始输出并归档到 steps（报告留存证据）；
4. 扩展 [core.py](vdcu/core.py) 的 `parse_vdev_info`：新增解析 container id / Usage memory / Dev busy percent 字段；
5. 占用观测的超时等待逻辑参考 FUN-016/17 的失败教训，改为轮询「任一占用字段」而非仅 Usage memory。

## 7. 风险与注意事项

- **观测字段可能根本不存在**：当前文档未记录 container id 字段，若实测无此字段，应作为"设计缺失"证据一并上报，而非仅当测试环境问题；
- **FUN-016/17 的连带失败**：占用保护缺失与互斥缺失同源，建议同一轮排查中一并复现取证；
- **exporter 影响**：若现场未部署 exporter，MX-005 仅记录 hy-smi 侧异常，影响评估留给驱动/监控团队；
- **证据完整性**：所有原始输出必须带时间戳存档，作为与驱动团队沟通的依据。
